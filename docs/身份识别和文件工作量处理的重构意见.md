ChatBoom 智能归因与身份识别重构指令
总体目标：重塑文件处理与工作量归因的核心逻辑。我们将从**“先解析文件名，再处理”的模式，转变为“先识别人员身份，再差异化处理”**的新模式。确保只有内部员工发布的文件才进行合规检查和工作量计算，客户发布的文件则不参与计算。

第一步：优化员工身份识别服务
目标：创建一个高效、可复用的员工身份识别服务，能够根据消息发送者的昵称或姓名，快速匹配到员工信息。

操作指令：

在 backend/ 目录下创建一个新的服务文件，例如 identity_service.py。

在该文件中，创建一个 IdentityService 类。

在 IdentityService 的 __init__ 方法中，实现一个员工缓存机制：

查询 EmployeeMapping 表中的所有员工数据。

创建一个字典（或多个字典）作为缓存，用于通过真实姓名 (real_name) 和微信昵称 (wechat_nickname) 快速查找到对应的 employee_id 和员工对象。例如：self.real_name_map = {'张三': emp_obj, ...} 和 self.nickname_map = {'San Zhang': emp_obj, ...}。

在 IdentityService 中，创建一个核心方法 def identify_employee(self, sender_name: str) -> EmployeeMapping | None:。

该方法接收一个 sender_name (消息发送者名称)。

查询逻辑：优先在 wechat_nickname 缓存中查找，如果找不到，再到 real_name 缓存中查找。

如果找到匹配的员工，返回该员工的 EmployeeMapping 对象；如果都找不到，则返回 None。

这个 IdentityService 将作为后续步骤中身份判断的基础。

第二步：改造聊天记录处理流程 ChatlogProcessor
目标：在处理每一条聊天消息的入口处，首先进行身份识别，并根据结果（员工/客户）对后续处理流程进行分发。

操作指令：

打开 backend/chatlog_processor.py 文件。

在 ChatlogProcessor 类的 __init__ 方法中，实例化 IdentityService，以便在处理器内部调用。

找到处理单条消息的核心方法（例如 process_message 或类似方法）。

在该方法的最开始，添加身份识别逻辑：

获取消息的发送者 sender_name。

调用 identity_service.identify_employee(sender_name) 方法来判断发送者身份。

重构文件处理逻辑：

原有的文件处理代码（通常是判断消息是否包含文件，然后调用 parser_service 或 file_validator）需要被包裹在一个条件判断中。

IF identify_employee 返回了一个员工对象：

说明是内部员工发布的文件。

继续执行原有的文件合规检查、解析、以及后续的 Asset 和 WorkloadRecord 生成逻辑。

在创建 FileRecord 时，务必将识别出的 employee_id 存入 file_records.employee_id 字段。

ELSE identify_employee 返回 None：

说明是外部客户发布的文件。

处理逻辑变更：

仍然创建 FileRecord 记录，但 employee_id 字段保持为空。

可以考虑为 file_records 表增加一个 source 字段（'internal' 或 'external'）来明确标识文件来源。

跳过所有后续的合规检查、工作量计算和 Asset 入库流程。这些文件只作为记录存在，不参与任何统计。

第三步：确保工作量计算只针对内部员工
目标：双重确认，确保工作量计算的源头 (Asset 和 WorkloadRecord 的生成) 严格排除了客户文件。

操作指令：

打开负责从 FileRecord 生成 Asset 的脚本（例如 backend/scripts/batch_import_assets_from_file_records.py）。

在该脚本的主循环中（遍历所有 file_records 的地方），增加一个前置检查。

在处理每一条 file_record 之前，检查其 employee_id 字段。

只有当 file_record.employee_id 存在（不为 None）时，才为该文件执行后续的 Asset 创建、workload_equivalent 计算和入库操作。

对于 employee_id 为空的 file_record（即客户文件），直接跳过，并可以打印一条日志，如 Skipping external file: [filename]。

最终验证
目标：确认新的身份识别与差异化处理逻辑已正确生效。

操作指令：

请完整审查以上所有步骤的修改。

清空数据库并重新导入一批包含员工和客户混合发言的聊天记录。

检查 file_records 表：确认员工发布的文件有关联的 employee_id，而客户文件该字段为空。

检查 assets 表和 workload_records 表：确认这两张表中只包含了员工发布的文件所生成的记录，客户文件的数据绝对没有被写入。

访问前端页面：确认“工作量分布”等图表中，只统计了内部员工的贡献，客户文件的工作量为零。

完成以上所有步骤后，我们的工具将能更智能、更准确地归因工作量，为后续更精准的团队负荷与项目健康度分析打下坚实的基础。
