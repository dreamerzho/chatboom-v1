### **团队负荷与项目健康度 \- 精准评估模型 (V2)**

核心理念转变：  
我们达成了一个至关重要的共识：工具的核心是洞察真实的工作行为，而非强制推行僵硬的规则。 因此，文件名规范将退居幕后，主要作为我们解析数据的“线索”，而不再是评价员工的“标尺”。我们的所有分析，都将围绕“团队负荷”与“项目健康”这两大核心目标展开。

### **第一部分：团队负荷评估模型 (Team Load Assessment Model)**

为了客观、公平地评估不同岗位的负荷，我们引入一个标准化的度量单位：**“工作量当量 (Workload Equivalent, WE)”**。所有产出和行为，都将被换算成WE，以便横向比较和累加。

#### **1\. 工作量当量 (WE) 换算总表**

这是我们根据你的规则制定的“价值换算表”，它是整个负荷计算的基础。

| 岗位 | 产出类型 | WE 计算规则 | 备注 |
| :---- | :---- | :---- | :---- |
| **文案** | 最终版-软文 | 1.0 WE / 篇 |  |
|  | 最终版-海报文案 | 0.33 WE / P |  |
|  | 最终版-视频脚本 | 1.0 WE / 篇 |  |
|  | 最终版-微楼书 | 2.0 WE / 篇 |  |
|  | 过程迭代版本 | 对应最终版WE \* 25% | 每次迭代的成本 |
| **设计** | 最终版-海报 | 1.0 WE / P |  |

#### **2\. 各岗位负荷指数 (Load Index) 计算方案**

现在，我们可以为每个角色定义一个更科学的、多维度的负荷指数：

##### **A. 创意岗位 (文案/设计) 负荷指数**

**负荷指数 \= (产出价值分) \+ (过程成本分)**

* **① 产出价值分 (Final Output WE):**  
  * **数据来源:** 周期内，所有被系统判定为“最终版”（3天内无更新的最后一个版本）的文件的WE总和。  
  * **业务价值:** 衡量员工的**有效产出**。这是其价值的核心体现。  
* **② 过程成本分 (Process Cost WE):**  
  * **数据来源:** 周期内，所有“过程迭代版本”的WE总和。  
  * **业务价值:** 衡量员工在达成最终产出过程中的**消耗**。这个分数越高，说明过程越“坎坷”。

##### **B. 项目经理 (PM) 负荷指数**

**负荷指数 \= (管理投入分) \+ (沟通成本分) \+ (策略产出分)**

* **① 管理投入分 (Management WE):**  
  * **数据来源:** 周期内，在内部群中提出有效“修改意见”的次数 \* 0.1 WE。  
  * **业务价值:** 量化PM对内部质量的把控和责任心。  
* **② 沟通成本分 (Communication WE):**  
  * **数据来源:** 周期内，在外部群发言的总次数 \* 0.05 WE。  
  * **业务价值:** 体现其在客户沟通上花费的精力。  
* **③ 策略产出分 (Strategy WE):**  
  * **数据来源:** 周期内，提交的“方案”类文档 \* 3.0 WE。  
  * **业务价值:** 衡量其核心策略产出。

##### **C. 客户执行 (AE) 负荷指数**

**负荷指数 \= (沟通对接分) \+ (流程贡献分)**

* **① 沟通对接分 (Client-Facing WE):**  
  * **数据来源:** 周期内，在外部群发言的总次数 \* 0.05 WE。  
  * **业务价值:** **核心指标**，直接反映其对接客户的繁忙程度。  
* **② 流程贡献分 (Process Contribution WE):**  
  * **数据来源:** (传递文件次数 \* 0.02 WE) \+ (内部修改意见次数 \* 0.1 WE)。  
  * **业务价值:** 体现其作为信息枢纽和内部品控的角色价值。

### **第二部分：工作复杂度与项目健康度模型**

这部分的目标是回答“**为什么返工多？**”以及“**这个项目还好吗？**”。

#### **1\. 智能返工归因模型**

这是你提出的最精彩的部分，我们必须实现它。

1. **第一步：建立“个人能力基线”**  
   * 系统为每位创意人员，在**所有项目**中计算一个长期的\*\*“平均迭代次数 (Avg. Personal Revisions)”\*\*。这代表了他/她的平均能力水平和工作习惯。  
2. **第二步：识别“项目难度异常”**  
   * 在分析**单个项目**时，系统会计算该员工在此项目中的\*\*“当前项目迭代次数 (Current Project Revisions)”\*\*。  
   * **归因判断逻辑：**  
     * **IF** 当前项目迭代次数 **远高于** 个人能力基线，**AND** 该员工在**其他项目**中表现正常，**THEN** 系统标记一次\*\*【项目难度预警】\*\*。这说明不是员工不行，是项目太难或客户要求太高。  
     * **IF** 当前项目迭代次数 **接近** 个人能力基线，说明表现符合其一贯水平。  
     * **IF** 一名员工的 个人能力基线 本身就远高于团队平均水平，系统可以标记\*\*【潜在技能错配】\*\*，提醒管理者关注。

#### **2\. 核心健康度指标**

* **① 平均定稿周期 (Time to Final):**  
  * **数据来源:** 从一个任务的v1版本出现，到其“最终版”被确定的总时长。  
  * **业务价值:** 直接衡量项目效率。周期过长意味着流程中存在堵点。  
* **② 迭代健康度 (Revision Health):**  
  * **数据来源:** 项目整体的“平均迭代次数”，以及被标记为【项目难度预警】的次数。  
  * **业务价值:** 评估项目的内部流程顺畅度。  
* **③ 沟通情绪参考 (Sentiment Reference):**  
  * **数据来源:** 聊天记录中的负面词汇频率。  
  * **业务价值:** **作为参考指标**，它不能下定论，但可以为数据分析提供“温度”和“背景”。当一个项目“迭代次数”和“定稿周期”都异常时，情绪指标可以帮助我们判断团队的承压状态。
